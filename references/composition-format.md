# Merry-slide Composition Format

Stage 2에서 만드는 `slide_plan.json`의 형식이다. 이 파일 하나가 CP3 프리뷰와 Stage 4A 빌더의 공통 입력이다.

프리뷰는 이 JSON을 실제 문구가 들어간 슬라이드로 렌더한다. 와이어프레임이 아니라 최종에 가까운 모습을 보여주므로, `content`를 비워두고 프리뷰를 띄우지 않는다. 빈 프리뷰는 검토 자료가 아니다.

## 최상위 구조

```json
{
  "title": "덱 제목",
  "slides": [ { "number": 1, "layout": "표지", "title": "...", "content": { } } ]
}
```

| 필드 | 설명 |
| --- | --- |
| `number` | 1부터 순차. 확정 저장 시 자동으로 다시 매겨진다 |
| `layout` | 아래 형식 이름 중 하나. **한글 이름을 그대로 쓴다** |
| `title` | 그 장이 증명하는 주장 한 문장. 명사형 제목이 아니라 액션 타이틀 |
| `content` | 형식별 구조. 아래 참고 |

## 형식 이름은 한글로 노출한다

내부 키(`two-col`, `section` 같은 영어 식별자)를 사용자에게 보여주지 않는다. 사용자는 그림과 한글 이름으로만 형식을 고른다.

| 형식 | 쓰임 |
| --- | --- |
| `표지` | 덱의 첫 장. 제목과 발행 주체 |
| `목차` | 전체 장 구성 |
| `간지` | 장이 바뀌는 구분 슬라이드 |
| `좌우 2단` | 두 내용을 나란히 비교하거나 이어서 |
| `표 중심` | 수치나 항목을 표로 정리 |
| `전폭 도식` | 구조나 흐름을 한 폭으로 크게 |
| `숫자 강조` | 핵심 수치 여러 개를 나열 |
| `단계 흐름` | 순서나 과정을 단계로 |
| `차트` | 수치 추이나 비중을 그래프로 |

이 목록은 실측 레퍼런스 덱 32장을 분류해서 나온 것이다. 다른 톤의 덱에서는 Stage 0에서 받은 대표 장표를 기준으로 형식을 새로 정의한다.

### 형식을 바꾸면 내용도 함께 옮겨진다

`layout`만 바꾸면 그 형식이 요구하는 필드가 없어 화면도 비고 빌드 결과도 빈 슬라이드가 된다. 프리뷰는 형식을 고를 때 기존 내용을 목표 형식에 맞게 변환한다.

변환의 출발점은 어떤 형식에서든 뽑아낼 수 있는 **항목 목록**이다. 우선순위대로 하나만 쓴다.

`stats` → `table.rows` → `flow` → `steps` → `left.body` + `right.body` → `items`

| 목표 형식 | 만들어지는 것 |
| --- | --- |
| `좌우 2단` | 항목을 절반으로 나눠 좌우 `body` |
| `표 중심` | `구분 / 내용` 2열 표 |
| `전폭 도식` | 항목 앞 4개를 `flow` 박스로 |
| `단계 흐름` | 항목 앞 5개를 `steps`로 |
| `차트` | 항목 앞 6개를 막대 차트로. 숫자를 못 찾으면 0 |
| `숫자 강조` | 항목 앞 3개를 `stats`로. 숫자가 없으면 값은 `—` |
| `목차` · `간지` | 항목 앞 5개를 `items`로 |
| `표지` | `intro`를 `subtitle`로 |

**기존 필드는 지우지 않는다.** `좌우 2단`에서 `단계 흐름`으로 바꿔도 `left`/`right`는 남아 있어 되돌아오면 원래 내용이 복구된다. 그 대신 여러 형식을 오가면 JSON에 쓰지 않는 필드가 쌓인다. 빌드는 `layout`이 가리키는 필드만 읽으므로 결과에는 영향이 없다.

변환 결과가 마음에 들지 않으면 프리뷰에서 고치거나, 형식에 맞는 `content`를 Stage 2에서 다시 쓴다. 변환은 출발점을 만들어 줄 뿐 최종 문안이 아니다.

## 본문 슬라이드 공통 필드

`좌우 2단`, `표 중심`, `전폭 도식`, `숫자 강조`, `단계 흐름`은 헤더 크롬을 공유한다.

| 필드 | 설명 |
| --- | --- |
| `content.section` | 좌상단 대분류 (예: `Ⅰ. 제안사 현황`) |
| `content.label` | 제목줄 앞 라벨 (예: `1-1. 기관 개요`). cyan으로 표시되고 `｜`로 제목과 이어진다 |
| `content.intro` | **리드 문단. 필수.** 아래 참고 |
| `content.introOptions` | 리드 문단 후보 배열. 프리뷰에서 골라 쓴다 |
| `content.note` | 슬라이드 하단 보조 설명 |
| `content.figure` | 이미지가 들어갈 자리. 아래 참고 |

### 리드 문단은 반드시 넣는다

구분선 바로 아래에 그 페이지 전체를 설명하는 문단이 들어간다. 레퍼런스 본문 슬라이드 **21장 전부**에 있는 요소이며(`y=1.503`, 12pt, 폭 10.336in), 빠지면 레퍼런스와 다른 덱이 된다.

- **길이는 150~200자.** 두세 문장으로 배경과 맥락을 설명한다.
- 제목줄을 되풀이하지 않는다. 제목은 주장이고, 리드 문단은 그 주장의 배경과 맥락이다.
- 아래 본문 블록에 있는 항목을 그대로 나열하지 않는다.

원본 레퍼런스 실측은 80~243자(중앙값 172자)로, 이 기준과 대체로 일치한다.

### 이미지 자리는 비워두지 않고 명시한다

빈 공간이 남으면 `figure`로 무엇이 들어갈지 적는다. 프리뷰에 빗금 박스로 표시되어 어떤 이미지를 준비해야 하는지 알 수 있다.

```json
{ "figure": { "caption": "두 서버 연결 구조도", "hint": "화면 → Express → Spring Boot → 저장소" } }
```

`좌우 2단`은 `left.figure` / `right.figure`로 한쪽에만 넣을 수 있다. 나머지 형식은 `content.figure`를 쓴다.

### 실제 이미지를 넣는 두 가지 방법

**프리뷰에서 고르기.** 프리뷰를 만들 때 사진 폴더를 함께 넘기면 그 사진들이 갤러리로 실린다.

```bash
node scripts/preview-composition.mjs --plan slide_plan.json --images ~/사진폴더 --serve
```

사진이 많으면 `--serve`를 쓴다. 정적 HTML은 사진을 전부 파일 안에 박아 넣어 200장이면 100MB를 넘지만, `--serve`는 사진을 따로 내주어 수백 KB에 그친다.

슬라이드의 이미지 자리를 클릭하면 갤러리가 열리고, 고른 사진이 브라우저에서 1600px / JPEG 품질 0.82로 줄여져 그 자리에 바로 표시된다. 확정 JSON에는 `data`(data URL)와 `w`/`h`로 저장된다.

폴더를 넘기지 않으면 OS 파일 선택창으로 대체되는데, 샌드박스 브라우저에서는 열리지 않을 수 있다. 폴더를 받는 쪽이 확실하다.

```json
{ "figure": { "caption": "...", "data": "data:image/png;base64,...", "w": 1200, "h": 700 } }
```

브라우저는 보안상 고른 파일의 **경로를 알려주지 않는다.** 그래서 경로가 아니라 내용을 심는다. 이미지가 많으면 JSON이 커지는데(장당 200~300KB), 경로 관리와 파일명 규칙이 사라지는 대가로 받아들인 것이다.

**폴더로 한 번에.** 이미지가 이미 준비되어 있으면 `page_<슬라이드번호>.png|jpg`로 폴더에 넣고 빌더에 넘긴다.

```bash
node components/build-from-plan.mjs --images ./images --out deck.pptx
```

한 장에 이미지 자리가 여러 개면 첫 번째 자리에만 붙는다. 프리뷰에서 이미 고른 이미지가 있으면 그쪽이 우선한다.

빌드 결과에 `images: { embedded, from_folder, empty, dropped_slots }`가 나온다. `empty`가 0이 아니면 아직 자리표시자로 남은 곳이 있다는 뜻이다.

**최종본을 낼 때는 빈 자리를 지운다.**

```bash
node components/build-from-plan.mjs --drop-empty-figures --out deck.pptx
```

사진이 없는 자리는 빗금 박스를 그리지 않는다. 한 줄이 통째로 비면 그 공간까지 콘텐츠가 차지하므로 표는 더 넓게, 도식은 더 크게 들어간다. 일부만 비어 있으면 채워진 칸만 남기고 격자는 유지한다.

옵션을 켜지 않으면 자리표시자가 그대로 남는다. 작업 중에는 무엇을 채워야 하는지 보이는 편이 낫기 때문이다.

### 이미지는 자리를 꽉 채운다

자리 크기에 맞춰 **늘리거나 줄여서** 넣는다. 여백을 남기지 않고, 원본을 잘라내지도 않는다.

비율이 다르면 그만큼 변형된다. 세로로 긴 사진을 가로로 넓은 자리에 넣으면 옆으로 퍼져 보인다. **자리에 맞는 비율의 사진을 준비하는 편이 낫다.**

자리 비율은 형식과 칸 수에 따라 정해진다. 표 3열이면 가로로 넓은 칸 3개, 좌우 2단이면 5.095in 폭의 칸 2개다. 프리뷰에서 실제 비율을 보고 고를 수 있다.

### 슬라이드를 꽉 채운다

콘텐츠 영역은 세로 `2.42in ~ 7.62in`다. 상단에만 내용을 몰아넣고 아래를 비우지 않는다.

각 형식의 콘텐츠는 **자기 내용에 맞는 높이만** 쓴다. 표는 행 수만큼, 도식은 박스 높이만큼, 단계와 숫자는 정해진 띠 높이만큼이다. 그리고 **남는 아래 공간은 자동으로 이미지 띠가 된다.** 선언된 `figure`가 없어도 자리를 열어 무엇을 넣어야 하는지 보여준다.

여백을 그냥 비워두지 않는 것이 이 톤의 기본이다. 내용이 모자라면 항목을 억지로 늘리지 말고 그 자리에 사진을 넣거나, 옆 장과 합친다.

### 아래 칸 수는 위 도형 수와 맞춘다

하단 이미지 띠는 한 덩어리가 아니라 **위 도형 개수만큼 나뉘고 x좌표와 폭이 위와 일치한다.**

| 위 | 아래 |
| --- | --- |
| 표 3열 | 이미지 3칸, 열 경계에 맞춤 |
| 도식 박스 4개 | 이미지 4칸 |
| 단계 5개 | 이미지 5칸 |
| 숫자 3개 | 이미지 3칸 |
| 좌우 2단 | 좌우 각 1칸 |

격자가 어긋나면 슬라이드가 흐트러져 보인다. 칸마다 다른 사진을 넣을 수 있으며 `content.figures` 배열에 순서대로 저장된다.

### 배치 좌표는 한 곳에서 온다

위 수치는 `components/base.mjs`의 `T.grid`에 모여 있다. 프리뷰와 빌더가 같은 토큰을 읽으므로 확정한 모습과 결과가 어긋나지 않는다. 좌표를 바꿀 일이 있으면 그 토큰만 고친다. 두 파일에 같은 숫자를 따로 적지 않는다.

## 형식별 content

### 표지

```json
{ "subtitle": "줄바꿈은 \n", "entity": "발행 주체" }
```

### 목차 / 간지

```json
{ "numeral": "Ⅰ", "items": ["소제목", "소제목"] }
```

`numeral`은 간지에서만 쓴다.

### 좌우 2단

```json
{
  "label": "1-1. 소분류",
  "left":  { "pill": "왼쪽 소제목", "body": ["항목", "항목"] },
  "right": { "pill": "오른쪽 소제목", "body": ["항목", "항목"] }
}
```

한쪽에 6개를 넘기지 않는다. 넘치면 장을 나눈다.

### 표 중심

```json
{
  "label": "2-1. 소분류",
  "pill": "표 제목",
  "table": { "headers": ["구분", "A", "B"], "rows": [["행", "값", "값"]] },
  "note": "표 아래 보조 설명"
}
```

**헤더 행은 늘리지 않는다.** 헤더는 열 이름을 다는 라벨 띠이므로 한 줄 높이로 고정하고 상하 여백을 최소화한다. 표가 세로 공간을 채워야 할 때 늘어나는 것은 본문 행이다.

레퍼런스 표 13개 실측: 헤더 행 중앙값 `0.275in`, 본문 행 중앙값 `0.171in`이며 본문은 내용에 따라 최대 `2.157in`까지 늘어난다. 헤더는 값이 거의 고정이고 본문만 변동한다.

헤더와 본문 행 높이가 같아 보이면 잘못 그린 것이다. 표 전체 높이를 지정하고 모든 행을 균등 분배하면 이 문제가 생긴다.

### 전폭 도식

```json
{
  "pill": "도식 제목",
  "flow": [ { "head": "단계명", "body": "설명\n줄바꿈 가능" } ],
  "note": "도식 아래 보조 설명"
}
```

`flow` 항목 사이에 화살표가 자동으로 들어간다. 3~4개가 적당하다.

### 단계 흐름

```json
{
  "pill": "흐름 제목",
  "steps": ["1단계", "2단계", "3단계", "4단계"],
  "note": "흐름 아래 보조 설명"
}
```

`steps`는 chevron으로 그려진다. 레퍼런스에 화살표 커넥터가 없으므로 선으로 잇지 않는다.

### 숫자 강조

```json
{
  "stats": [ { "label": "지표명", "value": "256", "unit": "개", "note": "산출 근거" } ],
  "note": "아래 보조 설명"
}
```

카드 배경을 넣지 않는다. 라벨 → 큰 숫자 → 각주 순서로 쌓는 것이 레퍼런스 문법이다.

### 차트

```json
{
  "pill": "차트 제목",
  "chart": {
    "type": "bar",
    "categories": ["2022", "2023", "2024"],
    "series": [{ "name": "투자 건수", "values": [41, 52, 63] }]
  },
  "note": "출처와 기준"
}
```

`type`은 `bar` `line` `pie` `doughnut` `gantt`를 쓴다. `column`은 `bar`와 같다.

**간트(`gantt`)는 데이터 구조가 다르다.**

```json
{
  "chart": {
    "type": "gantt",
    "gantt": {
      "unit": "월",
      "maxUnit": 9,
      "rows": [
        { "label": "선발 및 OT", "start": 0, "duration": 1 },
        { "label": "역량진단·멘토링", "start": 1, "duration": 3 }
      ]
    }
  }
}
```

`start`/`duration`은 같은 단위(주·월 등)의 숫자다. `maxUnit`을 생략하면 `start+duration` 최댓값으로 축을 잡는다. 누적 가로 막대로 그려지며 시작 구간은 투명, 기간 구간만 브랜드 색이다 — PowerPoint·엑셀에서 간트차트를 만드는 표준 방식이고, 일정이 바뀌면 사용자가 값만 고치면 된다.

**PowerPoint 네이티브 차트로 들어간다.** 이미지로 굽지 않으므로 사용자가 데이터를 직접 고칠 수 있다. 발표 직전에 숫자가 바뀌는 일이 흔하기 때문이다.

색은 브랜드 팔레트에서 순서대로 가져온다. 계열이 여럿이면 범례가 아래에 붙는다. 임의의 무지개색을 쓰지 않는다.

수치의 출처와 기준 시점은 `note`에 적는다. 차트만 있고 근거가 없으면 검증할 수 없다.

## 검증

프리뷰 생성 시 알 수 없는 형식 이름은 `unknown_formats`로 보고된다. 비어 있어야 한다.

```bash
node scripts/preview-composition.mjs --plan slide_plan.json --out preview.html
```
